    Distributed Training Strategies - Reference

    Overview Table

    Strategy What's Distributed Memory per GPU Communication Pattern Use Case Collectives Used Complexity
    Data Parallel (DP) Dataset only Full model All-reduce gradients after backward Models < 10B params, multiple GPUs all_reduce Low
    Tensor Parallel (TP) Model weights (horizontal split) 1/N of each layer All-reduce during forward/backward Models > 10B params, low latency inference all_reduce, all_gather Medium
    Pipeline Parallel (PP) Model layers (vertical split) 1/N of layers Point-to-point (activations) Very deep models, reduce memory send, recv High
    FSDP / ZeRO-3 Weights + gradients + optimizer states 1/N of everything All-gather weights, reduce-scatter gradients Models > 50B params, memory constrained all_gather, reduce_scatter Medium
    Hybrid (DP+TP+PP) All of the above Configurable Multiple patterns combined Production models (GPT-4, Claude) All collectives Very High

    Detailed Breakdown

    1. Data Parallel (DP)

    What it distributes: Only the dataset (mini-batches)

    How it works: - Each GPU has a full copy of the model - Each GPU processes a different mini-batch - After backward pass: all_reduce averages gradients across all GPUs - All GPUs update their models with averaged gradients

    Memory: 

    GPU 0: [full model] [batch 0]
GPU 1: [full model] [batch 1]
GPU 2: [full model] [batch 2]
GPU 3: [full model] [batch 3]

    Communication: - 1 all_reduce per training step - Volume: size of all gradients (~model size) - Happens after backward, not during forward

    When to use: - Model fits in GPU memory (< 40B params on A100 80GB) - You have multiple GPUs but model isn't huge - Simple to implement, linear scaling

    Examples: - Fine-tuning Llama 7B on 8 GPUs - Training ResNet on ImageNet - Most academic research

    Bandwidth requirement: Moderate (all-reduce gradients once per step)

    2. Tensor Parallel (TP)

    What it distributes: Model weights within each layer (horizontal split)

    How it works: - Each layer's weight matrix is split across GPUs (column-wise or row-wise) - Example: W [768, 3072] → GPU0: W[:, 0:1024], GPU1: W[:, 1024:2048], GPU2: W[:, 2048:3072] - During forward: each GPU computes partial result, then all_reduce or all_gather - During backward: similar pattern for gradient computation

    Memory: 

    GPU 0: [W_part0, gradW_part0] [full batch]
GPU 1: [W_part1, gradW_part1] [full batch]
GPU 2: [W_part2, gradW_part2] [full batch]

    Communication: - Multiple all_reduce / all_gather during forward and backward - Happens per layer, not just once per step - High communication frequency but small messages

    When to use: - Model too large for single GPU (> 40B params) - Low latency requirement (inference) - GPUs are on same node (NVLink high bandwidth)

    Examples: - GPT-3 175B inference (TP across 8 GPUs) - Megatron-LM training - Claude inference serving

    Bandwidth requirement: Very high (all-reduce per layer, needs NVLink or InfiniBand)

    Key insight: TP reduces memory but increases latency (more communication). Only worth it if model doesn't fit on single GPU.

    3. Pipeline Parallel (PP)

    What it distributes: Model layers (vertical split)

    How it works: - Model split into stages (groups of consecutive layers) - GPU 0: layers 0-29, GPU 1: layers 30-59, GPU 2: layers 60-89, GPU 3: layers 90-119 - Forward pass: activations flow from GPU0 → GPU1 → GPU2 → GPU3 - Backward pass: gradients flow back GPU3 → GPU2 → GPU1 → GPU0 - Micro-batching: split batch into smaller chunks to fill pipeline bubbles

    Memory: 

    GPU 0: [layers 0-29]  [activations chunk 0]
GPU 1: [layers 30-59] [activations chunk 1]
GPU 2: [layers 60-89] [activations chunk 2]
GPU 3: [layers 90-119][activations chunk 3]

    Communication: - Point-to-point send / recv (not collectives) - Transfer activations forward, gradients backward - Communication is sequential, creates pipeline bubbles (idle time)

    When to use: - Very deep models (> 100 layers) - Memory constraint but bandwidth limited (can't do TP) - Willing to accept pipeline bubbles (~20% idle time)

    Examples: - GPTNeo 20B (pipeline across multiple nodes) - Training models across slow interconnects

    Bandwidth requirement: Low (only send activations between neighbors)

    Key problem: Pipeline bubbles = GPUs sitting idle waiting for activations. Mitigated by micro-batching but never fully eliminated.

    4. FSDP / ZeRO-3 (Fully Sharded Data Parallel)

    What it distributes: Weights + gradients + optimizer states (everything)

    How it works: - Each GPU stores only 1/N of the model weights - Before forward: all_gather to reconstruct full layer weights - Compute forward, then discard weights (free memory) - Before backward: all_gather again for gradient computation - After backward: reduce_scatter to average gradients, each GPU keeps 1/N

    Memory: 

    GPU 0: [W_shard0, optim_state0] [full batch]
GPU 1: [W_shard1, optim_state1] [full batch]
GPU 2: [W_shard2, optim_state2] [full batch]
GPU 3: [W_shard3, optim_state3] [full batch]

    Communication: - all_gather before forward (reconstruct weights) - reduce_scatter after backward (shard gradients) - More communication than DP, but much less memory

    When to use: - Model > 50B params, doesn't fit in GPU memory - You have high bandwidth interconnect (NVLink, InfiniBand) - Want simplicity of data parallel but need more memory

    Examples: - Training Llama 70B on 8x A100 80GB - PyTorch FSDP, DeepSpeed ZeRO-3 - Meta's OPT-175B training

    Bandwidth requirement: Very high (all-gather every layer)

    Key insight: FSDP is DP with memory optimization. It trades communication for memory. With infinite bandwidth, it's equivalent to DP.

    5. Hybrid (DP + TP + PP)

    What it distributes: Everything (dataset, weights, layers)

    How it works: - Combine all strategies in a hierarchy - Example: 256 GPUs = 8 DP groups × 8 TP groups × 4 PP stages - Outer loop: data parallel (8 copies of model) - Middle loop: tensor parallel (split each layer across 8 GPUs) - Inner loop: pipeline parallel (split layers into 4 stages)

    Memory: 

    DP group 0, TP group 0, PP stage 0: [layer0-29, shard0] [batch_part0]
DP group 0, TP group 0, PP stage 1: [layer30-59, shard0] [batch_part0]
...
(Repeat for all 256 GPUs)

    Communication: - TP: all_reduce per layer (within TP group) - PP: send/recv between stages - DP: all_reduce gradients (across DP groups) - Communication is hierarchical and carefully orchestrated

    When to use: - Production training of models > 100B params - You have 100s or 1000s of GPUs - Maximum flexibility to tune memory/compute/communication trade-offs

    Examples: - GPT-4 training (estimated 1.76T params, 10k+ GPUs) - Claude 3 Opus training - PaLM 540B

    Bandwidth requirement: Extreme (needs NVLink + InfiniBand)

    Key challenge: Configuration complexity. Finding optimal DP/TP/PP split requires expertise and experimentation.

    Communication Primitives Reference

    Primitive What it does Used in Bandwidth cost
    all_reduce Average (or sum) tensor across all GPUs, all GPUs get result DP (gradients), TP (activations) N × tensor_size
    all_gather Each GPU has a shard, gather full tensor on all GPUs FSDP (weights), TP (partial results) N × shard_size
    reduce_scatter Average tensor, scatter shards to GPUs FSDP (gradients) N × tensor_size / N
    send / recv Point-to-point transfer between 2 GPUs PP (activations, gradients) tensor_size
    broadcast One GPU sends tensor to all others Weight initialization N × tensor_size
    barrier Synchronization point (no data transfer) Checkpointing coordination ~0

    Decision Tree

    Model size < 10B params?
├─ Yes → Use Data Parallel (DP)
└─ No → Model size < 100B params?
    ├─ Yes → Use FSDP or TP
    │   ├─ High bandwidth (NVLink)? → Use TP
    │   └─ Moderate bandwidth? → Use FSDP
    └─ No (> 100B params) → Use Hybrid (DP + TP + PP)
        └─ Tune configuration based on:
            - GPU memory (affects TP size, PP stages)
            - Interconnect bandwidth (affects DP/TP split)
            - Batch size (affects DP groups)

    Implementation Priorities for Sheaf

    Phase 1 (MVP) - Data Parallel

    • Why: Covers 80% of use cases (models < 10B params)
    • What: --distribute data-parallel --world-size N
    • Collectives needed: all_reduce, barrier
    • Effort: 2-3 weeks

    Phase 2 - FSDP

    • Why: Enables training 10B-100B models on moderate GPU clusters
    • What: Shard weights, all-gather before forward
    • Collectives needed: all_gather, reduce_scatter
    • Effort: 3-4 weeks

    Phase 3 - Tensor Parallel

    • Why: Low-latency inference for large models
    • What: Annotations :tensor-parallel on layers
    • Collectives needed: all_reduce (per layer)
    • Effort: 4-6 weeks

    Phase 4 - Hybrid

    • Why: Production-scale training (> 100B params)
    • What: Combine DP + TP + PP with hierarchical config
    • Effort: 2-3 months

    Further Reading

    • Megatron-LM paper (NVIDIA): Tensor + Pipeline parallelism
    • ZeRO paper (Microsoft): FSDP approach
    • GPipe (Google): Pipeline parallelism with micro-batching
    • PyTorch FSDP docs: Practical FSDP implementation
    • Alpa (UC Berkeley): Automatic parallelization (finds optimal strategy)

    Key Takeaway: There's no single "best" strategy. It depends on model size, GPU memory, interconnect bandwidth, and latency requirements. Production systems use hybrid approaches and tune configurations based on profiling.
