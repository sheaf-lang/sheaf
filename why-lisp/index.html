    Why a Lisp?

    Purity and immutability are not unique to Lisp. Haskell, OCaml, or any strict functional language would provide them. Lisp was chosen because it collapses the distinction between program and intermediate representation. In a homoiconic language, the source code is already a manipulable data structure, which means differentiation and compilation can operate as direct transformations of the program.

    Code as a manipulable structure

    Python does provide ways to inspect code (ast, inspect, torch.fx), but these are reconstructed representations, not the native form of the program. JAX derives its IR (JAXPR) via tracing; PyTorch 2.0 captures bytecode with TorchDynamo. Both are sophisticated engineering that reconstructs a functional graph from an imperative language.

    In Sheaf, the program is already the structure:

    (+ (@ x (get params :W)) (get params :b))

    This S-expression is simultaneously what the user writes, what the compiler traverses, and what the differentiator walks backward through. Differentiation is a source-to-source transformation applied before compilation, rather than something that happens during execution. The forward pass becomes forward-and-backward by rewriting the expression tree before codegen.

    The same applies to compilation. Lowering to StableHLO MLIR is a tree-to-tree translation. Sheaf starts from an IR where JAX and PyTorch must first derive one. In practice, pure functions that run in the interpreter tend to compile without modification.

    This comes at a cost: Sheaf restricts the language to a pure, statically-shaped subset. Dynamic control flow and mutation are not available inside compiled functions. This is the same trade-off JAX makes at the API level; Sheaf makes it at the language level.

    Macros as program transformations

    Because code is data, programs can generate programs at compile time. The defmodel macro produces a parameter initializer and forward function from a layer specification:

    (defmodel my-mlp
  [:l1 (linear 784 256) relu]
  [:l2 (linear 256 10) softmax])

    This expands into defn init-my-mlp and defn my-mlp-forward with the correct parameter tree and layer composition. The expansion is structural: it operates on the code as a list, not on strings or bytecode. In Python, equivalent code generation requires string manipulation, metaclasses, or decorator machinery.

    Macros are often criticized for making code harder to read. In Sheaf, their use is limited to structural transformations (architecture generation, batching via defbatch). Their expansion is deterministic and can be inspected. They do not alter control flow or introduce implicit behavior.

    Functional foundations

    Sheaf is a functional language: values are immutable, functions are pure by default, and random number generation follows an explicit key-based model. These properties simplify the autodiff implementation (the backward pass depends on explicit inputs and outputs, not implicit state) and make JIT caching safe (a function with the same inputs always produces the same outputs).

    These are properties of the functional paradigm, not of Lisp specifically. Sheaf's Lisp heritage provides the two capabilities described above: homoiconicity and macros. The functional discipline provides the rest. Together, they allow machine learning programs to be expressed, transformed, and compiled within a single, uniform representation.
