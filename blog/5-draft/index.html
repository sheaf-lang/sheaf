    Article 5 — Raw notes & metrics

    These are raw notes for blog article 5. Not prose yet — data, calculations, and narrative structure.

    Part 1: BareGPT optimizations (buffer cache, Arc tensor refcounting). Part 2: NanoGPT: porting a real model, JIT auto-compilation, MLIR codegen quality. Part 5: f32 interpreter + DeviceBuffer fast path.

    Context

    BareGPT: 4-layer transformer (d_model=256, n_heads=4), trained on Shakespeare. Autoregressive generation: 1000 tokens, one gpt-model call per token. Sheaf V2: interpreter orchestrates the generate loop, IREE executes gpt-model as compiled VMFB.

    The problem: marshalling overhead

    Every call to gpt-model(inputs, params, config) goes through this path:

    1. flatten_values(inputs) — recursively traverse dict/tuple structure → 27 flat tensors
    2. For each tensor: value_to_buffer_view() — convert f64→f32, allocate IREE buffer, memcpy
    3. iree_runtime_session_call_by_name() — actual computation
    4. Read back output buffer views → f32→f64 conversion

    For 1000 tokens: steps 1-2 run 27,000 times. But only 1 tensor (inputs, shape [128]) changes per iteration. The 26 param tensors (~8MB total, model weights) are identical every call.

    Cost breakdown (per call, estimated)

    Step Time × 1000 calls
    gpt-model computation (IREE) ~6ms 6.0s
    Param marshalling (26 tensors, f64→f32 + alloc + memcpy) ~2.5ms 2.5s
    Input marshalling (1 tensor, 128 floats) ~0.01ms 0.01s
    flatten_values dict traversal ~0.1ms 0.1s
    Interpreter overhead (reduce loop, get, print, nth) ~1.6ms 1.6s
    vm_list create/destroy + ref management ~0.1ms 0.1s
    Total ~10.3ms ~10.3s

    Measured total before optimization: 11.3s (broadly consistent).

    The fix: fingerprint-based buffer view cache

    Design

    Cache lives on IreeSession behind Mutex<HashMap<String, Vec<Option<CachedBufferView>>>>. Keyed by (function_name, flat_arg_position).

    Each cached entry stores:

    • A TensorFingerprint: shape + num_elements + 4 sample values as exact f64 bits
    • A retained *mut iree_hal_buffer_view_t (IREE refcounted, survives across calls)

    On each call:

    • Fingerprint every flat input tensor — O(1) per tensor (4 element reads)
    • Cache hit → reuse existing IREE buffer view (just retain_ref for the input list)
    • Cache miss → allocate new buffer view, release old cached one, store new one

    The fingerprint bug

    First version sampled [0, 1, 2, 3] (first 4 elements). Failed on BareGPT:

    append-and-roll shifts the context window left by 1, appends new token at end. With block_size=128 and a short prompt, the first ~100 elements are zeros for many iterations. Fingerprint saw [0, 0, 0, 0] → false cache hit → model received stale context → output was newlines.

    Fix: sample spread positions [0, n/4, 3n/4, n-1]. For a 128-element tensor: positions [0, 32, 96, 127]. The last element changes every iteration (new token appended). Bug fixed.

    This is a good blog anecdote: probabilistic caching is powerful but the sampling strategy matters. The fix is one line but required understanding the data access pattern.

    Refcounting fix (bonus)

    While implementing the cache, discovered a pre-existing refcount leak in the IREE call path:

    value_to_buffer_view() → bv refcount = 1
retain_ref(bv) → vm_ref on stack; bv refcount = 2
push_ref_retain(list, ref) → list retains; bv refcount = 3
release(bv) → bv refcount = 2
// stack vm_ref goes out of scope — no Drop impl → refcount stays at 2
// list release → refcount = 1 (leaked!)

    Fix: added iree_vm_ref_release to FFI bindings, call it after each push. Proper cleanup. Without the cache this leaked ~27 buffer views per call × 1000 calls = 27,000 leaked refs. With the cache, cached entries are properly released in IreeSession::Drop.

    Results

    Benchmark: 1000 tokens autoregressive generation (buffer cache only)

    Version Time Notes
    V1 (Python + JAX) 6.8s JAX jit-compiled, Python orchestration
    V2 before cache 11.3s Every call marshals all 27 tensors
    V2 after cache 7.7s 26/27 tensors cached, 1 marshalled per call

    Improvement: 32% faster (11.3s → 7.7s). Gap with JAX: 1.0s.

    (Further optimizations below close this gap entirely — see "The hidden cost" section.)

    What the cache eliminated

    • 26,000 IREE buffer allocations (26 params × 1000 calls)
    • 26,000 f64→f32 conversions of weight tensors
    • ~8MB × 1000 = 8GB of cumulative memcpy avoided
    • Replaced by 27,000 fingerprint comparisons (4 u64 compares each, ~ns)

    What remains (the ~1s gap)

    • Interpreter overhead (~1.6s): the generate loop is pure interpreter — reduce, let, get, print, append-and-roll, nth. JAX's Python loop is also interpreted, but CPython is faster at dict lookups than Sheaf's tree-walking interpreter.
    • flatten_values (~0.1s): recursive BTreeMap traversal to extract 27 leaf tensors, 1000 times.
    • vm_list lifecycle (~0.1s): create + populate + destroy an IREE input/output list per call.
    • Input tensor marshalling (~0.01s): 1 tensor × 128 floats × 1000 calls. Negligible.

    The perspective (after buffer cache, before Arc)

    Metric V1 (JAX) V2 (IREE)
    Runtime binary ~500MB (Python + JAX + XLA) 3.1MB (single static binary)
    100 tokens 2.2s 1.67s
    1000 tokens 6.8s 7.7s
    Compilation JIT at first call AOT (sheaf build)
    Param caching Automatic (JAX traces) Fingerprint-based buffer cache

    V2 is faster on short runs (100 tokens) because there's no JIT warmup. V2 is ~14% slower on long runs (1000 tokens) due to interpreter overhead in the generate loop. V2 is 160× smaller.

    The hidden cost: deep tensor cloning in the interpreter

    After the buffer cache brought us to 7.7s, we profiled the remaining gap (1.0s vs JAX). The cost breakdown pointed to "interpreter overhead (~1.6s)", but what was hiding in there?

    The discovery

    Sheaf's Value::Tensor stored ArrayD<f64> — ndarray's owned array type. Clone on ArrayD<f64> is a deep copy: allocates new memory, copies all elements.

    The interpreter's env.get() returns values by cloning them (the environment owns the value, the caller gets an independent copy). For scalars, strings, keywords — this is fine. For tensors, this means copying all tensor data on every variable access.

    In the generate loop, params (a dict of 26 weight tensors, ~8MB total) flows through the call chain:

    generate (reduce body)
→ env.get("params") → clone #1: 8MB deep copy
→ eval_call("generate-token", args)
→ env.set("params", val.clone()) → clone #2: 8MB deep copy
→ env.get("params") → clone #3: 8MB deep copy
→ eval_call("gpt-model", args) → IREE dispatch (no clone! refs only)

    Three deep clones of the entire param dict per token. Over 1000 tokens:

    • 3 × 8MB × 1000 = 24GB of unnecessary memory copies
    • 3 × 26 × 1000 = 78,000 malloc/free cycles

    At 150GB/s memory bandwidth, the memcpy alone costs ~160ms. The malloc/free overhead (system allocator fragmentation) adds another ~100ms. Total: ~260ms, but the real cost is worse — the single-threaded clone work blocks IREE's multi-threaded task system from overlapping computation.

    The fix: Arc>

    The Sheaf language is functionally immutable — values are never mutated in place. Operations always create new tensors. This is the perfect use case for reference counting.

    One-line type change:

    // Before
Tensor { data: ArrayD<f64>, dtype: Dtype }

// After
Tensor { data: Arc<ArrayD<f64>>, dtype: Dtype }

    Clone on Arc<T> is O(1) — an atomic increment of a reference counter, regardless of tensor size. An 8MB weight matrix and a 128-element input vector cost the same: ~1 nanosecond.

    The mechanical refactor

    The change touches 17 files but is entirely mechanical:

    • Constructors (Value::tensor_f32(arr), direct Value::Tensor { ... }): wrap in Arc::new()
    • Read access (data.shape(), data.iter(), data.len()): unchanged — Arc implements Deref<Target=ArrayD<f64>>, so all method calls auto-deref transparently
    • Mutation sites (rare — only perturb_leaf for numeric gradients, reduce_grad_to_param_shape): explicit deep clone with (**data).clone() before mutating

    37 constructor sites updated. Zero changes to read-only access patterns. The compiler catches every missed site — if you forget an Arc::new(), it's a type error, not a runtime bug.

    Impact: the numbers

    Version Wall time User time CPU%
    V2 before all optimizations 11.3s — —
    V2 + buffer cache 7.7s — —
    V2 + cache + zero-copy flatten 7.15s 28.1s 434%
    V2 + cache + Arc tensors (cold) 5.5s 26.3s 525%
    V2 + cache + Arc (steady-state) 4.85s 25.6s 590%
    V1 (Python + JAX) 6.8s 13.9s 233%

    V2 is now 29% faster than JAX on 1000 tokens. The 3.1MB binary beats the 450MB runtime.

    Two effects compound:

    1. User time dropped by 2.5s (28.1s → 25.6s). This is actual CPU time saved by eliminating deep copies. Arc refcount bumps cost ~1ns each vs ~50μs for an 8MB deep copy. The difference is 50,000×.

    2. CPU utilization jumped from 434% to 590%. The IREE local-task driver uses a thread pool (6 performance cores on M-series). Previously, the main thread spent significant time in single-threaded clone work between IREE calls. This serialized the pipeline: the worker threads had to wait for the main thread to finish copying tensors before the next IREE dispatch could start.

    With Arc, the inter-call overhead dropped to near zero. The main thread hands off work to IREE almost immediately, and IREE's worker threads stay saturated. Less serialization, more overlap, higher throughput. The Arc optimization didn't just save CPU time — it unlocked parallelism that was always available but couldn't be exploited.

    Cold vs steady-state: first run after build: 5.5s. Subsequent runs: 4.85s (stable). The ~0.7s difference is OS-level warmup: page cache (VMFB + weights file), allocator arenas, TLB entries. Not an IREE-level cache — just the usual first-access penalty for I/O and memory. JAX's 6.8s already includes its own cold start (JIT compilation on first call).

    Why this matters for language design

    This is a lesson about the interaction between language semantics and runtime performance.

    Sheaf is immutable-by-default. Values flow through function calls without mutation. The interpreter implemented this with deep copies — correct but expensive. Reference counting preserves the same semantics (immutability) while making copies free.

    The key insight: in a functional language where values are never mutated, ownership is a lie. There's no reason to give each scope its own physical copy of the data. A shared reference is semantically identical and physically optimal.

    JAX solved this differently: Python objects are mutable, but JAX values are opaque device arrays managed by XLA's runtime. The "copy" of a JAX array is already just a pointer bump. We arrived at the same destination from different starting points.

    Why the estimate was wrong

    We initially estimated ~170ms savings based on memcpy bandwidth analysis (24GB / 150GB/s). The actual savings were ~1.6s — almost 10× the estimate.

    The bandwidth calculation only counted the memcpy time for flat arrays. It missed:

    1. Malloc/free overhead: each of the 78,000 allocations goes through the system allocator. Fragmentation and lock contention in malloc dominate small-allocation patterns.
    2. Dict/Vec structure cloning: cloning a BTreeMap<String, Value> of 26 entries doesn't just clone the tensors — it clones the tree structure, all the string keys, and recursively clones nested dicts. The structural overhead compounds.
    3. Cache pollution: 24GB of write traffic through L1/L2 evicts hot data (IREE's compiled kernels, the interpreter's dispatch tables). The indirect cost of cache misses downstream is invisible in a bandwidth calculation.
    4. Parallelism starvation: the serialization effect (main thread blocked → worker threads idle) creates a multiplicative penalty that doesn't show up in single-thread analysis.

    The lesson: wall-clock profiling beats napkin math, especially when threading is involved.

    Final perspective

    Metric V1 (JAX) V2 (IREE + Arc)
    Runtime binary ~450MB (Python + JAX + XLA) 3.1MB (single static binary)
    100 tokens 2.2s 1.67s
    1000 tokens 6.8s 4.85s
    Compilation JIT at first call AOT (sheaf build)
    Param caching Automatic (JAX traces) Fingerprint-based buffer cache

    V2 is faster at all generation lengths. 145× smaller. Compiles ahead of time.

    Possible further optimizations (not implemented)

    1. Cache the vm_list itself: keep a persistent input list, only replace changed entries via iree_vm_list_set_ref. Would eliminate list create/destroy overhead.
    2. Skip flatten_values for unchanged args: cache the flattened tensor vector alongside the buffer views.
    3. Batch interpreter operations: the generate loop does ~10 interpreter operations between IREE calls. A lightweight "fast path" for reduce-over-range could help.
    4. Move generate loop to IREE: compile the entire generation loop (including sampling) as a single VMFB function. Would eliminate all per-token interpreter overhead. This is the nuclear option — essentially what JAX does with jax.lax.scan.

    Part 2 — NanoGPT: porting a real model, JIT, and MLIR quality

    Context

    NanoGPT: Karpathy's GPT-2 implementation, char-level Shakespeare. 6 layers, 384 dim, 4 heads, 65 vocab. Pre-trained weights from PyTorch. Faithful port to Sheaf — same weights, same architecture, same results.

    Benchmark: 100 tokens autoregressive generation. Reference: PyTorch (CPU) ~1.6s (~62 tk/s).

    The model in Sheaf

    ;; LayerNorm without bias
(defn layer-norm-nb [x gamma]
  (let [m (mean x :axis -1 :keepdims)
        v (var x :axis -1 :keepdims)]
    (* (/ (- x m) (sqrt (+ v 1e-5))) gamma)))

;; Causal self-attention
(defn causal-self-attention [x attn-p config]
  (let [D  (static (get config :n_embd))
        H  (static (get config :n_head))
        Hd (static (/ D H))
        T  (get (shape x) -2)
        W  (get-in attn-p [:c_attn :weight])
        Wq (slice W 0 D)
        Wk (slice W D (* 2 D))
        Wv (slice W (* 2 D) (* 3 D))
        q (swapaxes (reshape (@ x (transpose Wq)) [1 T H Hd]) 1 2)
        k (swapaxes (reshape (@ x (transpose Wk)) [1 T H Hd]) 1 2)
        v (swapaxes (reshape (@ x (transpose Wv)) [1 T H Hd]) 1 2)
        att (/ (@ q (swapaxes k -1 -2)) (sqrt Hd))
        att (softmax (where (== (tril (ones [T T])) 1.0) att -1e10) :axis -1)
        Wo (get-in attn-p [:c_proj :weight])]
    (@ (reshape (swapaxes (@ att v) 1 2) [1 T D])
       (transpose Wo))))

;; MLP block
(defn mlp-block [x mlp-p]
  (as-> x h
    (@ h (transpose (get-in mlp-p [:c_fc :weight])))
    (gelu h)
    (@ h (transpose (get-in mlp-p [:c_proj :weight])))))

;; Transformer block = LN + attention + residual + LN + MLP + residual
(defn transformer-block [x block-p config]
  (as-> x h
    (+ h (causal-self-attention
            (layer-norm-nb h (get-in block-p [:ln_1 :weight]))
            (get block-p :attn) config))
    (+ h (mlp-block
            (layer-norm-nb h (get-in block-p [:ln_2 :weight]))
            (get block-p :mlp)))))

    Key: the source code is idiomatic Sheaf. No compilation hints, no shape annotations. (static expr) marks compile-time constants (config values known at trace time).

    JIT auto-compilation

    The need

    sheaf build works but adds friction. User has to run a separate build step before running. Goal: transparent JIT — pure functions compiled on first call, cached, dispatched via IREE.

    Architecture

    eval_call("transformer-block", args, env)
  → try_iree_dispatch() → None (no vmfb)
  → try_jit_compile()
    → purity check (no side effects, no HOF)
    → type inference from concrete runtime args
    → inline called functions
    → lower dict access → GetTupleElement
    → resolve static constants
    → codegen → MLIR → iree-compile → VMFB
    → load into IreeSession
  → next call: try_iree_dispatch() → hits cached session

    What JIT compiles

    • transformer-block (the hot function — 600 calls for 100 tokens with 6 layers)
    • layer-norm-nb (called standalone outside transformer-block in gpt-forward)
    • causal-self-attention and mlp-block: inlined into transformer-block, not compiled separately
    • gpt-forward: too deep (nested dict params), falls back to interpreter
    • generate-token: has side effects (random-split), interpreter handles it
    • generate: has side effects (print), interpreter handles it

    Key implementation challenges

    Nested get resolution: (get-in attn-p [:c_attn :weight]) desugars at compile time to (get (get attn-p :c_attn) :weight). After function inlining, attn-p is bound to GetTupleElement("block-p", [0]). The outer get sees a GetTupleElement as first arg, not a Symbol → codegen fails.

    Fix: extended lower_inlined_gets to handle recursive resolution — when args[0] resolves to a GetTupleElement, use a reverse index map to reconstruct the path, extend with the new keyword keys, look up the full indices.

    Type inference from runtime values: value_to_stablehlo_type() infers tensor types directly from concrete argument values at call time. value_to_param_layout() detects nested dict structure for tuple flattening. No trace step needed — the runtime args are the trace.

    Fixing the buffer cache thrashing

    The 50/50 hit/miss ratio above is a design flaw, not an inherent cost.

    The buffer cache stores one entry per argument position per function. transformer-block is called 6 times per token (once per layer), each time with different weight tensors but the same argument positions. Layer 1's weights evict layer 0's, layer 2's evict layer 1's, and so on. By the next token, nothing is cached — permanent thrashing.

    The fix: expand from 1-entry to 8-entry per position, with MRU (most recently used) ordering. Each layer's weights coexist in the cache. After the first token, all 6 × 7 = 42 weight buffers are resident.

    // Before: Vec<Option<CachedBufferView>> — one slot per position
// After:  Vec<Vec<CachedBufferView>>    — up to 8 slots per position, MRU-ordered

    On cache lookup: linear scan of up to 8 entries (fingerprint comparison). On hit, swap to front. On miss, evict the oldest entry if at capacity.

    Results on Metal GPU (100 tokens, NanoGPT):

    Before (1-entry):
IREE dispatch profile (600 calls, 6736.2ms total):
  buffers:   4064.2ms (60.3%)  [hits: 4193, misses: 4207]
  call:      2329.2ms (34.6%)
  output:     342.5ms ( 5.1%)
→ 7.64s wall

After (8-entry):
IREE dispatch profile (600 calls, 2983.6ms total):
  buffers:    385.8ms (12.9%)  [hits: 7763, misses: 637]
  call:      2246.0ms (75.3%)
  output:     351.6ms (11.8%)
→ 3.90s wall

    Buffer allocation time: 4064ms → 386ms (10.5× reduction). Cache hit rate: 50% → 92%. Wall time: 7.64s → 3.90s (1.96× speedup).

    The 637 remaining misses are the activations (intermediate x tensor), which change at every call — these can never be cached. The 7763 hits are the model weights, now uploaded once to the GPU and reused across all 100 tokens.

    Why 8 and not 6? The function signature flattens dict args into individual tensors, and some positions see both weight tensors (6 variants) and config scalars (1 variant) depending on the calling context. 8 accommodates this with headroom for other calling patterns.

    Device tensor passthrough

    After the multi-entry cache fix, the remaining buffer cost is the activation tensor x — it changes every call, so it can never be cached. But there's a subtlety: x at the input of transformer-block layer N is exactly the output of layer N-1. The data is already on the GPU. We're pulling it back to the CPU (D2H), then immediately pushing it back (H2D).

    The fix: retain output buffer views from the last IREE call. On the next call, before allocating a new buffer, check if any input matches a retained output (by fingerprint). If so, reuse the on-device buffer directly — zero-copy passthrough.

    // After each IREE call: retain output buffer views
iree_hal_buffer_view_retain(bv);
new_output_bvs.push((fingerprint, bv));

// Before each IREE call: check retained outputs first
let output_hit = prev_outputs.iter()
    .find(|(fp, _)| fp.matches(val))
    .map(|(_, bv)| *bv);

    Results on Metal GPU (100 tokens, NanoGPT, cached VMFBs):

    Before (no passthrough):
  buffers:    385.8ms (12.9%)  [hits: 7763, misses: 637]
→ 3.06s wall

After (output passthrough):
  buffers:     72.4ms ( 2.8%)  [hits: 8302, misses: 98]
→ 2.82s wall

    Buffer time: 386ms → 72ms (5.4× reduction). Cache misses: 637 → 98 (−85%). The remaining 98 misses are the genuinely new tensors (initial token embedding, first-call weights). Wall time: 3.06s → 2.82s — modest because GPU compute dominates at 85%.

    Note: D2H still happens (we need the output values on the CPU for the interpreter). The saving is only on the H2D side: we avoid re-uploading data that's already on the GPU.

    MLIR codegen quality: mean CSE

    The problem

    LayerNorm source:

    (let [m (mean x :axis -1 :keepdims)
      v (var x :axis -1 :keepdims)]
  (* (/ (- x m) (sqrt (+ v 1e-5))) gamma))

    var is implemented as mean((x - mean(x))^2). The internal mean(x) call inside var duplicates the explicit (mean x) that's already bound to m.

    Before fix: 3 stablehlo.reduce ops per LayerNorm (sum-for-mean, sum-for-mean-in-var, sum-for-var). After fix: 2 stablehlo.reduce ops per LayerNorm (sum-for-mean reused, sum-for-var).

    Impact: 2 LayerNorms × 6 layers × 100 tokens = 1200 unnecessary reductions eliminated.

    The fix

    Register-level CSE cache on StableHLOEmitter:

    // In StableHLOEmitter struct:
reduce_mean_cache: HashMap<(Register, usize, bool), (Register, StableHLOType)>,

// In emit_reduce_mean():
let cache_key = (*input, axis_usize, keepdims);
if let Some(cached) = self.reduce_mean_cache.get(&cache_key) {
    return cached.clone();
}
// ... compute mean ...
self.reduce_mean_cache.insert(cache_key, (result_reg, sum_ty.clone()));

    When emit_var calls emit_reduce_mean on the same register+axis that was already computed by the explicit (mean x), it gets the cached result. Zero new MLIR ops emitted.

    Why not a general CSE pass?

    Could run a generic CSE pass on the MLIR output (IREE has one). But catching it at the emitter level is simpler: it's a 6-line cache, specific to the known pattern (var reuses mean). General CSE on StableHLO would require hash-consing all ops — overkill for one known pattern.

    MLIR codegen quality: QKV matmul — the GPU trap

    The hypothesis

    Source code slices the fused QKV weight matrix and does 3 separate matmuls:

    (let [W  (get-in attn-p [:c_attn :weight])   ;; [3D, D] = [1152, 384]
      Wq (slice W 0 D)                        ;; [384, 384]
      Wk (slice W D (* 2 D))                  ;; [384, 384]
      Wv (slice W (* 2 D) (* 3 D))            ;; [384, 384]
      q  (@ x (transpose Wq))                 ;; matmul #1
      k  (@ x (transpose Wk))                 ;; matmul #2
      v  (@ x (transpose Wv))]                ;; matmul #3
  ...)

    PyTorch does: qkv = x @ W.T (one matmul [1,T,D] × [D,3D] → [1,T,3D]), then splits. 3 matmuls → 1 fused matmul. Should be faster, right?

    The experiment

    Implemented fused version. Added (slice tensor start end :axis -1) to slice along the last axis of the [1,T,3D] result.

    (let [W   (get-in attn-p [:c_attn :weight])
      qkv (@ x (transpose W))                 ;; one matmul → [1,T,3D]
      q (slice qkv 0 D :axis -1)              ;; [1,T,D]
      k (slice qkv D (* 2 D) :axis -1)
      v (slice qkv (* 2 D) (* 3 D) :axis -1)]
  ...)

    The result: neutral on CPU

    Version IREE call time (700 calls) Avg/call
    3 separate matmuls 4850–5140ms ~8.5ms
    1 fused matmul + 3 slices 4570–5290ms ~8.5ms

    No measurable difference. The variance between runs (~10%) swamps any signal.

    Why it doesn't help on CPU

    The intuition "one big matmul is faster" comes from GPU optimization:

    • GPU: kernel launch overhead dominates small operations. Fusing 3 kernels into 1 saves significant launch + synchronization cost.
    • CPU (IREE local-task): no kernel launch overhead. IREE tiles matmuls into thread-pool tasks. Three [256,384]×[384,384] matmuls have better L2 cache utilization than one [256,384]×[384,1152]. Each 384×384 weight block fits in L2; the fused 384×1152 may not.

    Plus the fused version adds 3 stablehlo.slice ops to extract the Q,K,V chunks — extra memory traffic that offsets any fusion benefit.

    Decision: keep the 3-matmul version. It's more readable, and equally fast on CPU. This will change when we add GPU support — the fused version is the right default for GPU.

    Part 3 — Autodiff: compiling the backward pass

    Context

    Part 2 ended with inference at 2.82s (Metal) for 100 tokens. But inference is only half the story — training requires gradients. NanoGPT's training loop uses value-and-grad: compute the loss and its gradient w.r.t. all parameters in one call.

    Without compilation, value-and-grad falls back to the interpreter, which computes numeric gradients by finite differences: perturb each of the 10.65M parameters by ε, re-run the full forward pass, measure Δloss/ε. That's 10.65 million forward passes per training step. Result: ~10.9 seconds per step — and that's already optimized, because the forward pass itself is JIT-compiled.

    PyTorch does the same step in 86ms. The gap: 127×.

    The goal: compile value-and-grad into a single VMFB — forward + backward in one dispatch, no interpreter in the loop.

    Sheaf's symbolic AD

    Sheaf already has a symbolic automatic differentiation engine (grad_simplified). Given a CompiledExpr and a variable name, it returns a new CompiledExpr representing the derivative. It knows the chain rule, product rule, and the derivatives of all StableHLO ops (matmul, softmax, exp, etc.).

    For a simple function like:

    (defn f [x] (* x (sin x)))
;; grad_simplified(body, "x") produces:
;; (+ (* 1 (sin x)) (* x (cos x)))

    This is textbook symbolic differentiation. It works well for small expressions.

    The plan: compile value-and-grad end-to-end

    The pipeline we needed:

    1. Extract the closure passed to value-and-grad
2. Inline all function calls (gpt-forward, transformer-block, etc.)
3. Lower dict access to tuple indices (params[:transformer][:h] → GetTupleElement(p, [0,1]))
4. Apply symbolic AD to get the gradient expression
5. Codegen both forward and backward into one MLIR module
6. iree-compile → VMFB → cache

    Steps 1-3 already worked (from the JIT infrastructure in Part 2). Step 5-6 are the existing codegen. The hard part was step 4: making symbolic AD work on a GPT-scale expression.

    Obstacle 1: reduce blocks AD

    GPT-forward stacks 6 transformer blocks with reduce:

    (reduce (fn [h bp] (transformer-block h bp config))
        x
        (get-in params [:transformer :h]))

    grad_simplified returned zero — it didn't know how to differentiate through reduce.

    The fix: symbolic unrolling. Before AD, transform the reduce into an explicit Let chain:

    let __r_0 = transformer-block(x, params.transformer.h[0], config)
let __r_1 = transformer-block(__r_0, params.transformer.h[1], config)
...
let __r_5 = transformer-block(__r_4, params.transformer.h[5], config)
result = __r_5

    This works because n (the number of layers) is known at compile time from the parameter type — it's a tuple of 6 elements. After unrolling, the expression is a plain Let chain that grad_simplified can handle.

    Implementation: ~140 lines in transforms.rs. The unroller resolves the collection's StableHLO type, determines n, and generates n iterations with proper symbol substitution.

    Obstacle 2: alias propagation

    After function inlining, the code contained:

    let params = p    ;; inlined binding
(get-in params [:transformer :h])  ;; uses the alias

    The dict-lowering pass (lower_inlined_gets) didn't recognize params as an alias for the root parameter p. It only resolved (get p :key), not (get params :key) where params is bound to p via Let.

    Fix: propagate Symbol aliases through Let bindings. When a Let binding maps a name to a bare Symbol that's either a known parameter or an existing alias, register the new name as an alias too. 5 lines, but it took a while to diagnose.

    Obstacle 3: dynamic shapes from cons

    The loss function (cross-entropy-loss in nn.shf) builds reshape dimensions dynamically:

    (reshape logits (cons -1 (cons V '[])))
;; builds the shape [-1, V] at runtime

    The codegen expected a literal Vector for the shape argument. cons chains weren't resolved during constant folding.

    Fix: teach resolve_static_constants to flatten (cons head tail) chains into Vectors. Also handle (int expr) casts and -1 dimension inference (infer the missing dimension from the input tensor's total size, like NumPy).

    Obstacle 4: missing gradient rules

    The initial AD engine only knew derivatives for basic arithmetic and matmul. GPT-forward uses many more ops. Added gradient rules for:

    • sqrt → 1/(2√f) · df/dx
    • tanh → (1 - tanh²(f)) · df/dx
    • gelu → approximate derivative using tanh formulation
    • reshape, swapaxes → pass-through (shape manipulation, no data transformation)
    • where(cond, a, b) → route gradient to a or b based on condition
    • slice → pass-through
    • neg → negate the gradient
    • abs → sign(f) · df/dx
    • log-softmax → specialized Jacobian

    About 80 lines of gradient rules total.

    It compiles! ... then crashes

    After all these fixes, the pipeline ran to completion for the first time. The VMFB compiled (154 KB). The forward pass produced correct loss values.

    But the gradients were all zero. Then, after fixing the gradient rules, a new problem: the process consumed 165 GB of RAM and nearly crashed the machine (60 GB swap on a MacBook with 36 GB physical memory).

    The wall: exponential expression growth

    This was the fundamental problem, and it took us a session of debugging to understand it.

    Sheaf's CompiledExpr is a tree — an algebraic data type where each node owns its children. When the chain rule produces:

    d/dx (f * g) = f' * g + f * g'

    It clones the entire subtrees f and g into the result. If f is itself a deep expression (say, 6 layers of transformer computations), every application of the chain rule duplicates the entire subtree.

    For GPT with 6 unrolled transformer blocks and 58 parameter leaves, the gradient expression grows exponentially. A back-of-the-envelope calculation:

    • Forward expression after unrolling: ~3000 nodes
    • Each chain rule application at depth d duplicates ~3000/d nodes
    • 58 parameters × 6 layers of nesting → gradient expression with billions of nodes
    • Each node is a heap-allocated enum → 165 GB

    This is not a bug — it's an architectural limitation. Symbolic AD on trees cannot work for deep computation graphs.

    How PyTorch and JAX solve this

    Both frameworks avoid this problem by operating on graphs with sharing, not trees.

    PyTorch uses a runtime tape. During the forward pass, each operation records itself and its backward function on a tape. loss.backward() walks the tape in reverse, computing concrete gradient tensors (not expressions). Each intermediate value exists once in memory. This is reverse-mode AD at execution time.

    JAX uses a compiled IR called jaxpr — essentially SSA form (Static Single Assignment: each variable defined exactly once). jax.grad transforms a forward jaxpr into a backward jaxpr. Variables are names (like SSA registers), not trees — referencing a variable doesn't copy anything.

    The key insight: in both systems, sub-expressions are shared by reference. When the chain rule needs f in both f' * g and f * g', it references the same node/register in both places. The gradient is the same size as the forward pass — O(n), not O(2^n).

    The solution: ANF + reverse-mode AD

    We had three options:

    Option A — Quick fix: transform the expression tree to ANF (Administrative Normal Form) before AD. ANF names every sub-expression in a Let binding. The existing forward-mode AD then operates on Symbols (names) instead of trees — no duplication. This fixes the OOM but computes gradients one parameter at a time (58 passes for 58 parameters).

    Option B — Proper solution: transform to ANF, then implement reverse-mode AD. Walk the bindings in reverse order, accumulate adjoint contributions for all parameters in a single pass. One backward pass regardless of parameter count. This is what JAX does.

    Option C — Codegen-level AD: emit the backward pass directly in MLIR during code generation, building a tape of SSA registers during forward emission. This is closer to what PyTorch does. But it couples AD logic with codegen — two concerns that should be separate.

    We chose B. The reasoning:

    1. Separation of concerns: AD is a transformation from IR to IR. Codegen translates IR to MLIR. Mixing them (option C) creates a monolith that's harder to test, debug, and evolve independently.

    2. Same output: B and C produce identical MLIR. The backward pass is the same set of operations regardless of which stage generates them. There's no performance difference in the compiled output.

    3. Natural fit: Sheaf already has an IR (CompiledExpr) and a transform pipeline (inline → lower → unroll → resolve). Adding ANF conversion and reverse-mode AD is another transform in the same pipeline. The codegen stays unchanged.

    4. JAX validates this architecture: JAX's jax.grad operates on jaxpr (their IR), not on the XLA backend. The separation has scaled to production use at Google. PyTorch's approach (tape at runtime) makes sense for an eager-execution framework without a compilation phase — but Sheaf is a compiler.

    What ANF looks like

    Before ANF (tree):

    (* (+ a b) (- (+ a b) c))
;;        *
;;       / \
;;      +   -
;;     / \ / \
;;    a  b +  c    ← (+ a b) duplicated!
;;        / \
;;       a   b

    After ANF (flat Let chain):

    (let [t0 (+ a b)
      t1 (- t0 c)
      t2 (* t0 t1)]
  t2)
;; t0 appears twice, but it's just a name — no tree duplication

    The ANF form is structurally identical to SSA / MLIR registers. Each binding computes one operation. The gradient pass walks these bindings in reverse:

    ;; Forward bindings:
;;   t0 = a + b
;;   t1 = t0 - c
;;   t2 = t0 * t1     (the output)
;;
;; Reverse-mode AD (adjoint accumulation):
;;   dt2 = 1.0                        (seed)
;;   dt1 += dt2 * t0                  (from t2 = t0 * t1, ∂/∂t1)
;;   dt0 += dt2 * t1                  (from t2 = t0 * t1, ∂/∂t0)
;;   dt0 += dt1 * 1                   (from t1 = t0 - c, ∂/∂t0)
;;   dc  += dt1 * (-1)                (from t1 = t0 - c, ∂/∂c)
;;   da  += dt0 * 1                   (from t0 = a + b, ∂/∂a)
;;   db  += dt0 * 1                   (from t0 = a + b, ∂/∂b)

    One pass, all gradients computed, O(n) expression size. This is the algorithm we're implementing next.

    Implementing reverse-mode AD

    to_anf: flattening the tree

    The ANF transform is a recursive descent that "names" every non-trivial sub-expression. The implementation (autodiff/reverse.rs, ~80 lines) walks the CompiledExpr tree and lifts operations out into a flat Let:

    fn anf_rec(expr, bindings) -> CompiledExpr {
    match expr {
        FunctionCall(name, args) => {
            // First, ANF-convert each argument
            let flat_args = args.map(|a| anf_rec(a, bindings));
            // Then bind the call itself to a fresh name
            let name = fresh_anf_name();  // __a_0, __a_1, ...
            bindings.push((name, FunctionCall(name, flat_args)));
            Symbol(name)
        }
        Let { bindings: inner, body } => {
            // Flatten nested Lets into the same level
            for (name, val) in inner {
                bindings.push((name, anf_rec(val, bindings)));
            }
            anf_rec(body, bindings)
        }
        // Leaves (Symbol, Float, Integer...) stay as-is
        _ => expr
    }
}

    For GPT, this produces 556 forward bindings — one per operation. The tree that was thousands of nodes deep (with duplicated subtrees) becomes a flat sequence where each sub-expression appears exactly once.

    reverse_grad: walking backward

    The reverse-mode pass (autodiff/reverse.rs, ~500 lines) takes the ANF bindings and produces new bindings for the backward pass:

    pub fn reverse_grad(bindings, result_sym, wrt_symbols, shapes) -> Vec<(String, CompiledExpr)> {
    let mut adjoints: HashMap<String, CompiledExpr> = HashMap::new();
    adjoints.insert(result_sym, Float(1.0));  // seed

    // Walk bindings in reverse order
    for (name, expr) in bindings.iter().rev() {
        let adj = adjoints.remove(name).unwrap_or(Float(0.0));
        // Distribute adj to this binding's inputs
        distribute_adjoint(expr, adj, &mut adjoints, shapes);
    }

    // Collect the adjoints for the requested parameters
    wrt_symbols.map(|s| adjoints.remove(s))
}

    The core complexity is in distribute_adjoint — it needs a gradient rule for every operation Sheaf supports. For GPT, that means:

    Operation Gradient rule Notes
    +, - pass adj through with unbroadcast
    * adj * other_operand with unbroadcast
    / adj / y, -adj * x / y²
    @ (matmul) adj @ B^T, A^T @ adj
    reshape reshape(adj, original_shape)
    slice pad(adj, zeros, offsets)
    transpose transpose(adj)
    softmax adj * s - s * sum(adj * s) Jacobian-vector product
    log-softmax adj - softmax * sum(adj)
    gelu full tanh-approximation derivative 6 intermediate ops
    mean(x, :axis) adj / axis_size (broadcast back)
    var(x, :axis) adj * 2 * (x - mean) / n
    sum(x, :axis) broadcast adj back to input shape
    exp, log, sqrt standard calculus
    layer-norm pass through (macro-expanded before AD)

    For GPT, reverse_grad produces 1639 backward bindings from the 556 forward ones. Combined with the forward pass, that's ~2200 named operations compiled into a single MLIR module.

    The unbroadcast problem

    This was the subtlest bug. In the forward pass, + silently broadcasts:

    pos_embedding[1, 256, 384] + token_embedding[4, 256, 384]
→ result[4, 256, 384]    (pos_embedding broadcast along dim 0)

    In the backward pass, the adjoint of result has shape [4, 256, 384]. If we pass it directly as the gradient for pos_embedding, we get a shape mismatch — the gradient is [4, 256, 384] but the parameter is [1, 256, 384].

    The fix: sum_to_shape. After computing each gradient contribution, check if the adjoint's shape differs from the operand's shape. If so, sum over the broadcast dimensions:

    fn maybe_unbroadcast(adj, target_shape) -> CompiledExpr {
    if adj.shape != target_shape {
        sum_to_shape(adj, target_shape)  // reduce broadcast dims
    } else {
        adj
    }
}

    sum_to_shape is implemented as a codegen builtin that emits stablehlo.reduce ops: first reducing extra leading dimensions, then reducing dimensions where the target has size 1 (with keepdims). This mirrors what JAX's _unbroadcast does internally.

    Every binary op (+, -, *, /, @) wraps its gradient contributions with maybe_unbroadcast. Without this, roughly half the backward ops would produce shape-mismatched MLIR.

    The slice gradient

    The forward pass slices into the embedding table: slice(embedding_matrix, [token_ids, :]). The gradient of a slice is a sparse update: the adjoint goes at the slice's offset, padded with zeros everywhere else.

    We implement this with stablehlo.pad:

    slice_grad(adj[4,256,384], target_shape=[65,384], start=[3,0])
→ pad(adj, 0.0, low=[3,0], high=[58,0])
→ tensor[65,384]   // zeros except rows 3..7 which contain adj

    This avoids scatter operations (which IREE handles poorly for small slices) and keeps the computation purely functional.

    The GELU gradient

    GELU uses the tanh approximation:

    gelu(x) = 0.5 * x * (1 + tanh(√(2/π) * (x + 0.044715 * x³)))

    Its derivative is not trivial. The gradient rule emits 6 intermediate operations:

    let k = 0.0356774                           // 3 * 0.044715 * √(2/π)
let inner = √(2/π) * (x + 0.044715 * x³)
let t = tanh(inner)
let sech2 = 1 - t²                          // sech²(inner)
let dinner = √(2/π) * (1 + k * x²)         // d(inner)/dx
gelu_grad = adj * 0.5 * ((1 + t) + x * sech2 * dinner)

    Getting this wrong produces gradient explosion — the loss goes to 10²⁰ within a single step. We caught this by checking gradient magnitudes: correct gradients for GPT should be in the 1e-4 to 1e-5 range.

    The full pipeline

    After all the fixes, the complete VAG compilation pipeline:

    1.  Extract closure (loss-fn + captures)
2.  Type inference (Value → StableHLOType for each param)
3.  lower_get_calls (dict access → tuple indices)
4.  inline_function_calls (expand transformer-block, attention, etc.)
5.  lower_inlined_gets (resolve get on inlined expressions)
6.  unroll_reduces (reduce over 6 blocks → 6 explicit Let bindings)
7.  re-lower gets (resolve new get calls from unrolling)
8.  resolve_static_constants (evaluate compile-time constants)
9.  to_anf (tree → flat Let chain: 556 bindings)
10. reverse_grad (forward bindings → 1639 backward bindings)
11. Codegen forward + backward into one MLIR module (~2500 lines)
12. iree-compile → VMFB (cached to __sheaf__/)
13. Dispatch: (loss, grad_tuple) in a single GPU call
14. tuple_to_dict / tuple_to_list: reconstruct Sheaf's Dict/List structure

    Steps 6, 9, 10, and 14 are new in this session. Steps 1-5, 7-8, 11-12 existed from the forward-only JIT. The backward pass reuses the exact same codegen — reverse_grad produces CompiledExpr nodes like FunctionCall("matmul", [...]), and the existing codegen knows how to emit those as StableHLO ops. No new MLIR emission code was needed for any standard op.

    The new codegen builtins (sum_to_shape, slice_grad) are backward-specific operations that don't exist in the forward vocabulary. They emit 5-10 lines of StableHLO each.

    Part 4 — Fusing the training step

    Context

    Part 3 ended with three separate GPU dispatches per training step:

    value-and-grad  →  clip-by-global-norm  →  adam-step
   (91ms)              (4.4ms)               (35ms)

    Each dispatch means: flatten Sheaf dicts to IREE buffers, call into Metal, unflatten back to Sheaf dicts. Between dispatches, the interpreter runs — evaluating let bindings, calling assoc, extracting values with get. That's 57ms of overhead per step, on top of the 92ms of actual GPU work.

    The question: can we compile the entire train-step function — forward, backward, gradient clipping, and Adam update — into a single VMFB?

    (defn train-step [state x y config]
  (let [loss-fn   (fn [p] (cross-entropy-loss (gpt-forward x p config) y))
        [loss g]  ((value-and-grad loss-fn) (get state :params))
        g         (clip-by-global-norm g 1.0)
        [p m v t] (adam-step (get state :params) g
                             (get state :m) (get state :v) (get state :t)
                             6e-4 0.9 0.95 1e-8)]
    (assoc state :params p :m m :v v :t t :loss loss)))

    One function, one GPU dispatch, zero intermediate marshalling.

    Why it didn't compile before

    The JIT compiler has a purity check: it rejects functions that contain higher-order function calls (HOFs) like map, filter, grad, value-and-grad. These depend on runtime closures that can't be statically compiled.

    train-step contains (value-and-grad loss-fn) — an HOF call. So the JIT skips it entirely. The three sub-functions compile individually (VAG, clip, adam), but the outer function stays interpreted.

    Even if we lift the HOF restriction, there's a deeper problem. The compiler's InlineValueAndGrad form uses grad_simplified — a symbolic differentiation engine. grad_simplified can differentiate simple expressions (matmul, add, exp), but it can't handle the full GPT forward pass: get on nested dicts, reduce over transformer blocks, LambdaCall for attention sublayers. All marked "undiffable."

    The pipeline that works for VAG is reverse_grad — the ANF-based reverse-mode AD from Part 3. But that pipeline lives in jit.rs, wired up specifically for standalone VAG compilation. It's not available inside the codegen that processes InlineValueAndGrad.

    The approach: reverse-mode AD inside codegen

    The fix: when the codegen encounters InlineValueAndGrad and the lambda body contains ops that grad_simplified can't handle, switch to the reverse_grad pipeline instead.

    The key insight is that everything needed already exists — it just needs to be wired up in a different place. to_anf, reverse_grad, generate_binding are all available. The difference is that instead of emitting a separate MLIR module (like standalone VAG does), we emit the forward and backward passes inline in the same module as the rest of train-step. The gradients become registers in the same scope — clip and adam operate on them directly, no marshalling.

    The lowering pipeline problem

    The first attempt immediately failed. The lambda body inside InlineValueAndGrad needs the same lowering passes as any top-level function:

    inline_function_calls  →  lower_get_calls  →  unroll_reduces  →  resolve_static_constants

    But none of these passes recurse into InlineValueAndGrad nodes. They all have an other => other.clone() catch-all that copies the node verbatim. The lambda body was raw, unlowered — full of FunctionCall("get", ...) nodes instead of GetTupleElement, unresolved constants like (static (get config :n_embd)), and un-unrolled reduces.

    The fix: replicate the full lowering pipeline inside generate_inline_value_and_grad, after inlining but before the ANF conversion:

    1. Build index maps for lambda params from the outer scope's tuple_key_layouts
2. lower_get_calls + lower_inlined_gets (dict access → tuple indices)
3. unroll_reduces (reduce over 6 transformer blocks → 6 explicit Let bindings)
4. Re-lower gets (resolve new get calls introduced by unrolling)
5. resolve_static_constants (config values → integer literals)
6. to_anf → reverse_grad → generate forward + backward bindings

    Each step uncovered a new failure mode. lower_get_calls needs index maps for the lambda param p, which maps to the params subtree of state — those maps had to be derived from the outer scope's layout info. unroll_reduces needs type information for the accumulator. resolve_static_constants needs shapes for tuple leaves that only exist after get-lowering. Five iterations of "fix one, hit the next wall."

    New codegen: assoc

    train-step returns (assoc state :params p :m m :v v :t t :loss loss) — a dict update. The codegen had never seen assoc before, because no previously-compiled function modified a dict.

    In MLIR, a dict is a tuple. assoc becomes tuple surgery: extract each element from the input tuple, replace the ones being updated, and construct a new tuple. The codegen resolves key names to tuple indices via tuple_key_layouts, generates the replacement values, and emits a single stablehlo.tuple with the right mix of originals and replacements.

    The random key problem

    After all the codegen fixes, train-step compiled to MLIR and IREE successfully. But at runtime:

    warning: 'train-step' compiled for 132 tensors but called with 133

    Off by one. The culprit: (random-key 42) in the training state. Sheaf represents RNG keys as Value::List([Int(lo), Int(hi)]) — a list of two integers. The type inference sees this as f32_tensor([2]) (one tensor), but the runtime flattener counts each integer separately (two values). A mismatch baked into the Value representation.

    The fix was structural: RNG keys are effects, not computation. They shouldn't flow through the compiled VMFB at all. We moved the key out of the state dict and into the (interpreted) reduce loop that calls train-step. The compiled function sees only tensors and scalars — no lists of integers.

    Return value reconstruction

    One more issue: the compiled train-step returns a tuple, but the caller expects a dict. The JIT has a layout reconstruction system that maps tuple types back to their dict structure. But train-step's return type doesn't exactly match its input type — Adam promotes state.t from ScalarI64 to scalar_f32. The type-based layout lookup failed silently.

    The fix: when the return type is a tuple with the same number of elements as a known parameter layout, register that layout for the return type too. Structure-based matching instead of exact type matching.

    What the fusion changed

    The MLIR module for the fused train-step contains everything: the full GPT forward pass (6 transformer blocks, each with attention + MLP), the reverse-mode backward pass (1639 ANF bindings), gradient clipping (global norm + rescale), and the Adam optimizer update (for all 58 parameter tensors).     • 6 interpreter-to-IREE transitions per step (3 dispatches × flatten + unflatten)

    The 2.85× gap with PyTorch is now dominated by the GPU kernel itself. IREE's Metal backend vs Apple's MPS — different compilers targeting the same hardware. This is outside Sheaf's control, but IREE is actively improving its Metal support.

    On Sheaf's side:

    • Buffer cache misses on step 1: 135 misses = 26.6ms. A warm-up call or lazy GPU migration would eliminate this.
    • CUDA benchmarks: Metal is Apple-only. The real comparison is on NVIDIA hardware, where IREE targets CUDA/Vulkan and PyTorch uses cuDNN.

    Part 5: f32 interpreter + DeviceBuffer fast path

    Context

    Two changes, measured on GPT-2 124M (batch=1, block=64, Metal GPU):

    1. f32 interpreter: Value::Float changed from f64 to f32. Eliminates f64-to-f32 conversion at the IREE boundary. Every tensor was being cast on every call.
