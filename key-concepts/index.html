    Architecture

    Sheaf is a Lisp dialect for machine learning that compiles to native code. Programs are lowered to StableHLO, the same intermediate representation used by JAX and TensorFlow, then compiled and executed via IREE. The result is a standalone binary (~3MB) that runs training loops without Python, without a framework runtime, and without JIT warm-up after the first call.

    This document describes the compilation pipeline, the automatic differentiation system, and the runtime architecture. It is intended both as a reference for users who want to understand what happens when they run sheaf run model.shf, and as a map for contributors working on the compiler.

    Compilation Pipeline

    When you call a function in Sheaf, the compiler transforms your source code through several intermediate representations before generating machine code. Understanding this pipeline helps explain both the capabilities and limitations of the system.

    Source (.shf)
    │
    ▼
┌─────────┐
│  Parse  │  -> SheafValue AST
└────┬────┘
     ▼
┌──────────┐
│ Compile  │  -> CompiledExpr IR
└────┬─────┘
     ▼
┌─────────┐
│ Codegen │  -> StableHLO MLIR
└────┬────┘
     ▼
┌──────────────┐
│ iree-compile │  -> VMFB bytecode
└──────┬───────┘
       ▼
┌──────────────┐
│ IREE Runtime │  -> Metal / CUDA / CPU
└──────────────┘

    From Source to AST

    The parser reads Sheaf source and produces a SheafValue AST, a tree of s-expressions with source location tracking for error messages. At this stage, the code is still in its original form:

    ;; Source
(defn linear [params x]
  (+ (@ x (get params :W))
     (get params :b)))

    From AST to CompiledExpr

    The compiler transforms the AST into CompiledExpr, an intermediate representation that resolves macros, expands special forms, and performs basic validation. Dict accesses like (get params :W) are lowered to tuple element extraction with stable field ordering:

    ;; CompiledExpr (simplified)
Let {
  bindings: [],
  body: FunctionCall {
    name: "+",
    args: [
      FunctionCall { name: "@", args: [Symbol("x"), GetTupleElement { param: "params", indices: [0] }] },
      GetTupleElement { param: "params", indices: [1] }
    ]
  }
}

    The field ordering (:W -> index 0, :b -> index 1) is determined at compile time from the runtime dict structure. This ordering is stable across calls with the same dict layout.

    From CompiledExpr to StableHLO

    The code generator translates CompiledExpr to StableHLO MLIR. Type information flows from runtime arguments: when you first call linear with concrete tensors, the JIT infers shapes and generates typed MLIR:

    func.func @linear(%arg0: tensor<768x768xf32>, %arg1: tensor<768xf32>,
                  %arg2: tensor<4x768xf32>) -> tensor<4x768xf32> {
  %0 = stablehlo.dot_general %arg2, %arg0,
       contracting_dims = [1] x [0] : (tensor<4x768xf32>, tensor<768x768xf32>) -> tensor<4x768xf32>
  %1 = stablehlo.broadcast_in_dim %arg1, dims = [1] : (tensor<768xf32>) -> tensor<4x768xf32>
  %2 = stablehlo.add %0, %1 : tensor<4x768xf32>
  return %2 : tensor<4x768xf32>
}

    Note how the dict parameter params has been flattened to two separate tensor arguments (%arg0, %arg1), and the bias addition includes an explicit broadcast.

    From MLIR to Machine Code

    The final stage invokes iree-compile to lower StableHLO to device-specific code. IREE performs fusion, memory planning, and kernel selection for the target backend. The output is a VMFB (Virtual Machine FlatBuffer) containing the compiled kernels.

    The IREE toolchain is downloaded automatically on first compilation (~300MB, cached in ~/.sheaf/toolchain). Once cached, subsequent compilations are fast, typically under a second for individual functions.

    JIT Compilation

    Functions are compiled transparently on first call. This means you never explicitly invoke the compiler; instead, the runtime detects when a function lacks compiled code and triggers compilation automatically.

    The JIT performs the following steps:

    1. Type inference: Examines runtime arguments to determine tensor shapes and dtypes
    2. Dict lowering: Converts dict parameters to tuples with stable field ordering
    3. Inlining: Expands calls to user-defined functions into the caller's body
    4. Codegen: Generates StableHLO MLIR from the inlined expression
    5. Compilation: Invokes iree-compile with the appropriate backend flags
    6. Caching: Stores the resulting VMFB by content hash for future calls

    Subsequent calls with the same argument shapes dispatch directly to the cached VMFB. Cache invalidation is automatic: if the source code changes, the content hash changes, and the function is recompiled.

    Backend Selection

    Sheaf selects the compilation backend based on available hardware:

    Platform Primary Backend Fallback
    macOS Metal CPU
    Linux CUDA CPU
    Other CPU -

    If the primary backend fails (missing drivers, unsupported operations), Sheaf automatically falls back to CPU compilation. You can override backend selection with the SHEAF_DEVICE environment variable:

    SHEAF_DEVICE=cpu sheaf run model.shf    # Force CPU backend
SHEAF_DEVICE=metal sheaf run model.shf  # Force Metal backend

    Cache Layout

    Compiled functions are cached in the __sheaf__ directory alongside your source files:

    __sheaf__/
├── manifest.json     # Maps function names to content hashes
├── forward.vmfb      # Compiled forward pass
├── loss.vmfb         # Compiled loss function
└── loss-vag.vmfb     # Compiled value-and-gradient closure

    The manifest tracks content hashes to detect staleness. You can safely delete the entire __sheaf__ directory to force recompilation.

    Automatic Differentiation

    Sheaf implements automatic differentiation through a system called VAG (Value And Gradient). When you call (value-and-grad f), the compiler generates a single function that computes both the forward pass and the gradients in one execution. There is no separate backward pass, no tape.

    The Differentiation Pipeline

    The autodiff system transforms expressions through several stages:

    CompiledExpr (forward only)
    │
    ▼
┌────────┐
│ to_anf │  -> Flat Let chain (every subexpr named)
└───┬────┘
    ▼
┌──────────────┐
│ reverse_grad │  -> Forward bindings + backward bindings
└──────┬───────┘
       ▼
┌─────────┐
│ Codegen │  -> Single MLIR function computing (loss, gradients)
└─────────┘

    ANF Conversion

    Before differentiation, expressions are converted to Administrative Normal Form (ANF). In ANF, every intermediate computation is bound to a name, producing a flat sequence of let-bindings:

    ;; Original expression
(+ (* x y) (* y z))

;; After ANF conversion
(let [__anf_0 (* x y)
      __anf_1 (* y z)
      __anf_2 (+ __anf_0 __anf_1)]
  __anf_2)

    This transformation is crucial for efficient gradient computation. In the original tree form, computing gradients would require duplicating subexpressions: the gradient of (+ a a) naively expands to (+ (grad a) (grad a)), which doubles the work. With ANF, each subexpression is computed exactly once, and gradients accumulate into named adjoint variables.

    Reverse-Mode Differentiation

    The reverse_grad pass walks the ANF bindings in reverse order, emitting adjoint contributions for each operation. For a binding v = f(a, b), the pass computes:

    • dL/da += dL/dv * df/da (contribution to a's gradient)
    • dL/db += dL/dv * df/db (contribution to b's gradient)

    The adjoint of the final output (the loss) is seeded with 1.0. Gradients accumulate as the pass works backward through the bindings.

    Here is a concrete example. Given this forward pass:

    (defn loss [W x y]
  (mean (** (- (@ x W) y) 2)))

    The VAG system generates code equivalent to:

    ;; Forward pass (ANF)
(let [__anf_0 (@ x W)           ; prediction
      __anf_1 (- __anf_0 y)      ; error
      __anf_2 (** __anf_1 2)     ; squared error
      __anf_3 (mean __anf_2)]    ; loss

  ;; Backward pass
  (let [__grad_3 1.0                                    ; dL/d(loss) = 1
        __grad_2 (/ __grad_3 N)                         ; dL/d(squared) = 1/N
        __grad_1 (* __grad_2 (* 2 __anf_1))             ; dL/d(error) = 2*error/N
        __grad_0 __grad_1                               ; dL/d(pred) = dL/d(error)
        __grad_W (@ (transpose x) __grad_0)]            ; dL/dW = x^T @ dL/d(pred)

    [__anf_3 __grad_W]))  ; return (loss, gradient)

    Both passes are fused into a single MLIR function, so intermediate values computed in the forward pass are directly available for the backward pass without recomputation.

    Supported Operations

    Gradient rules are implemented for most tensor operations. The following categories are fully differentiable:

    Category Operations
    Arithmetic +, -, *, /, **, neg
    Matrix @ (matmul), transpose
    Shape reshape, swapaxes, slice
    Activations relu, gelu, sigmoid, tanh, softmax, log-softmax
    Reductions sum, mean, var
    Elementwise exp, log, sqrt, abs
    Control where, maximum, minimum
    Iteration reduce, scan, first

    reduce and scan are unrolled before differentiation when the collection size is statically known. Higher-order functions with dynamic closures (map, filter) are not differentiable.

    Lowering Structural Operations

    Some Sheaf constructs (get, reduce, scan) are structural rather than numerical. They manipulate collections or extract fields, operations that don't map directly to StableHLO. Before differentiation, these are lowered to pure tensor operations:

    Dict access (get) is lowered by lower_get_calls, which transforms (get params :key) into GetTupleElement nodes with static indices:

    ;; Before lowering
(get params :W)

;; After lowering (assuming :W is at index 0)
GetTupleElement(params, [0])

    Iteration (reduce, scan) is unrolled by unroll_reduces when the collection size is statically known:

    ;; Before unrolling
(reduce (fn [h bp] (transformer-block h bp config))
        x
        (get-in params [:transformer :h]))  ;; 6 layers

;; After unrolling
(let [__r_0 (transformer-block x layer0 config)
      __r_1 (transformer-block __r_0 layer1 config)
      ...
      __r_5 (transformer-block __r_4 layer5 config)]
  __r_5)

    After lowering and unrolling, the expression contains only tensor operations that the reverse-mode AD can differentiate.

    StableHLO Code Generation

    The code generator translates CompiledExpr into StableHLO MLIR, the portable IR used by the XLA ecosystem. This section covers the key transformations.

    Virtual Tuples

    Sheaf dicts and tuples are conceptually single values, but StableHLO represents them as multiple tensor arguments. The codegen maintains "virtual tuples", internal bookkeeping that tracks which MLIR arguments correspond to which dict fields.

    ;; Sheaf function with dict parameter
(defn forward [params x]
  (+ (@ x (get params :W)) (get params :b)))

    // Generated MLIR: dict flattened to separate arguments
func.func @forward(%arg0: tensor<768x768xf32>,  // params[:W]
                   %arg1: tensor<768xf32>,       // params[:b]
                   %arg2: tensor<4x768xf32>)     // x
    -> tensor<4x768xf32> {
  // ...
}

    The field-to-index mapping is recorded in a manifest, allowing the runtime to correctly pass dict fields as positional arguments.

    Broadcasting

    Binary operations follow NumPy broadcasting semantics. When operand shapes differ, the codegen emits explicit stablehlo.broadcast_in_dim operations to align shapes before the computation:

    ;; Sheaf: add bias (768,) to activations (4, 768)
(+ activations bias)

    // Generated MLIR: explicit broadcast
%0 = stablehlo.broadcast_in_dim %bias, dims = [1]
     : (tensor<768xf32>) -> tensor<4x768xf32>
%1 = stablehlo.add %activations, %0 : tensor<4x768xf32>

    Constant Propagation

    Scalar values and dict fields known at compile time are propagated through the expression. This is essential for shape-dependent operations like reshape and slice, which require static dimensions in StableHLO:

    ;; config is a dict with {:n_embd 768, :n_head 12}
(reshape x [(get config :batch) (get config :n_head) -1])

    If config is available at compile time, the codegen resolves the shape to concrete integers. If not, compilation fails with an error indicating which values couldn't be resolved.

    IREE Runtime

    The runtime interfaces with IREE (Intermediate Representation Execution Environment) via FFI. IREE provides the actual execution engine: it loads compiled VMFBs and dispatches them to the appropriate hardware backend.

    IreeSession

    Each compiled function runs within an IreeSession, which manages:

    • The IREE runtime instance
    • The HAL (Hardware Abstraction Layer) device (CUDA, Metal, Vulkan or CPU)
    • Loaded VMFB modules
    • Buffer allocation and caching

    Sessions are created automatically when needed and reused across function calls.

    DeviceBuffer

    By default, tensor data lives on the host (CPU memory). When a tensor is passed to a JIT-compiled function, it's transferred to device memory. The DeviceBuffer type represents tensors that remain on device between calls, avoiding repeated host-device transfers in training loops:

    Step 1: params (host) -> DeviceBuffer (H2D transfer)
Step 2: DeviceBuffer -> forward -> DeviceBuffer (no transfer)
Step 3: DeviceBuffer -> backward -> DeviceBuffer (no transfer)
...
Step N: DeviceBuffer -> host (D2H transfer, only for checkpointing)

    This optimization is automatic. The runtime tracks which tensors are already on device and skips redundant transfers.

    Buffer Cache

    Input tensors are cached by identity: if the same tensor Arc is passed to the same function argument position, the runtime reuses the existing device buffer. This handles the common case where model parameters don't change between training steps.

    The cache maintains multiple entries per position to handle weight sharing (e.g., transformer layers that share embedding matrices) without thrashing.

    Optimizations

    Sheaf is routinely benchmarked against PyTorch on identical architectures with shared weights. The following optimizations are implemented:

    Runtime optimizations:

    • Arc tensor refcounting: Tensors use Arc<ArrayD<f32>> instead of owned arrays. Cloning a tensor is O(1) regardless of size. This eliminates 24GB of redundant memory copies per 1000 inference tokens during benchmarks on GPT-2.

    • Fingerprint-based buffer cache: Input tensors are fingerprinted (shape + 4 sample values) and cached by position. Unchanged tensors reuse existing device buffers across calls.

    • Multi-entry MRU cache: Each argument position holds up to 8 cached buffers with most-recently-used ordering. This prevents thrashing when transformer layers share a compiled function but use different weights.

    • DeviceBuffer passthrough: Output buffers from one dispatch are retained on GPU. When passed as input to the next dispatch, no host-device transfer occurs.

    • f32 native: The interpreter operates in f32 throughout. No f64-to-f32 conversion at the IREE boundary.

    Codegen optimizations:

    • Virtual tuples: Dict and tuple parameters are flattened to individual MLIR arguments. No stablehlo.tuple ops are materialized; tuples complicate compiler passes and are being phased out of StableHLO.

    • Mean CSE: Common subexpression elimination for reduce_mean. When var(x) internally computes mean(x), it reuses any existing mean computation on the same tensor.

    • Fused value-and-grad: Forward and backward passes compile to a single MLIR function. Intermediate activations flow directly to the backward pass without rematerialization.

    • Fused train-step: When possible, the entire training step (forward, backward, gradient clipping, optimizer update) compiles to a single GPU dispatch.

    Performance Characteristics

    Sheaf is benchmarked against PyTorch on GPT-2 124M with identical weights. Current measurements on Apple M5 Pro:

    Training (forward + backward + Adam):

    Configuration Time per step vs PyTorch
    Interpreter 10.9s 272x
    JIT (Metal) 533ms 4.2x
    PyTorch (MPS) 127ms baseline

    Inference (100 tokens autoregressive):

    Configuration Time ms/token
    JIT (Metal) 746ms 7.0
    PyTorch (MPS) 390ms 3.9

    The remaining gap is primarily in IREE's Metal backend maturity versus Apple's MPS. We track this upstream and contribute fixes where possible (see IREE #19Due, PR #20117).

    Profiling

    To understand where time is spent, run with --blame:

    sheaf --blame train.shf

    This prints a timing report showing time spent in each function, both total and self time, plus a call tree. See the profiler example on the home page for sample output.

    Known Limitations

    • Control flow in JIT: if and while expressions inside JIT-compiled functions cause fallback to the interpreter. Conditional logic must currently live outside the hot path.

    • Static shapes: All tensor shapes must be known at compile time. Dynamic batch sizes require recompilation when the batch size changes.

    • Metal backend maturity: IREE's Metal backend is less optimized than CUDA. Some operations may be significantly slower on Apple GPUs than on NVIDIA hardware.

    • Memory management: Large models may exceed device memory. There is no automatic model sharding or gradient checkpointing yet.
